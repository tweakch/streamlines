# Prototype-Werkstatt

Self-contained HTML prototypes. Everything gets tried here first — game mechanics, UI
elements, screen layouts, storytelling beats, design directions. Fiddle until happy,
then port the result "statically" into `app/`. The app never receives untested ideas.

## Rules

- Every prototype is **one `.html` file**: inline CSS + JS, no build step, no external
  dependencies beyond Google Fonts and `kit/` (see below). Double-click to open, or serve
  the folder (`npx http-server prototype`) if the browser blocks `file://` features.
  **One exception, and it is narrow:** a library that cannot be retyped may be vendored
  into `vendor/<name>-<version>/` — currently only `three.js` core, for the 3D renderer
  evaluation. Read [`vendor/README.md`](vendor/README.md); it carries the reasoning, the
  no-addons rule, and the consequence that ES modules do **not** load over `file://`
  (such a draft needs `npx http-server` or Chrome's `--allow-file-access-from-files`, and
  must say so on screen when it fails to boot).
- New prototypes build on the **`kit/`** — the shared UI primitives. Don't retype
  buttons, tabs, toasts or the hex grid; look at `kit/kit-demo.html` first.
- A prototype does not need to be a whole game. A single screen, a nav element, a
  dialogue card, or a color/typography study is a valid prototype.
- Naming: `<topic>-v<N>[-<variant>].html`, kebab-case. New iteration on the same
  topic = new version; the superseded file moves to `archive/`.
- Prototypes are throwaway by design: global mutable state, string templates and
  copy-paste are fine here. Quality standards apply at port time, not draft time.

## Directories

### `kit/`
The shared UI primitives — **read [`kit/README.md`](kit/README.md) before building a new
prototype.** Tokens (day/night/werkbank), controls, panels, feedback, the hex grid, and
the knowledge-document layout, plus `SOT.*` helpers for query params, toast, overlays,
tabs and seeded randomness. `kit/kit-demo.html` is the living styleguide: every primitive
in every state.

A primitive earns its place here only after it looked the same in **two or more**
prototypes. The kit follows the prototypes, never the other way round.

Because drafts now reference `../kit/…`, a file loses its self-containedness while it
lives in `drafts/`. It gets it back on the way out — see *Lifecycle*.

### `drafts/`
Active experiments — the current best version of each topic. At most one live file
per topic. This is the only directory whose files may be edited in place.

**Exception:** `drafts/stromlinien-handbuch.html` is a *generated* file — its
source lives in `handbuch/` (see below); never edit the HTML by hand.

### `handbuch/`
The markdown sources of the Handbuch — one file per chapter, cards as
`## Titel {status}`, plus the page `template.html`. Read
[`handbuch/README.md`](handbuch/README.md) for the dialect. Rebuild with
`npm run compose:handbuch` (in `app/`); `npm run check:handbuch` detects drift
between markdown and the committed HTML.

### `ab/`
A/B comparisons when a decision needs two (or more) competing variants. One subfolder
per experiment:

```
ab/<experiment>/
  a-<label>.html
  b-<label>.html
  NOTES.md        ← the question being tested, observations per variant, the DECISION and why
```

When decided: winner moves to `drafts/` (as the topic's next version), losers move to
`archive/`. The `NOTES.md` moves to `archive/<experiment>-NOTES.md` so the reasoning
survives.

### `archive/`
Immutable history. Superseded versions, rejected variants, and drafts that were ported
land here — never edited, never deleted. Keep the version suffix and, where helpful,
add what replaced it (e.g. `-v1-squares` after the hex upgrade).

**Archived files carry no `kit/` references.** Inline the kit on the way in, otherwise
the file silently changes appearance whenever the kit evolves — and immutable history
that mutates is worthless:

```
node prototype/kit/inline.mjs prototype/drafts/<topic>-v1.html --out prototype/archive/<topic>-v1.html
```

## Lifecycle

```
idea → drafts/<topic>-v1.html          (built on kit/, see kit/README.md)
     → (optional) ab/<topic>-…/ with variants + NOTES.md
     → happy? → port into app/ → inline the kit → move html to archive/, update ledger
     → rejected? → inline the kit → straight to archive/, update ledger
```

| `plaettchen-pfade-v1.html` | `drafts/` | active, **neu** | **Die Arena — ein Plättchen, seine Ringe, seine Sorte, sein Höhenfeld, sein Lauf, seine Seen — und Quellen, die Wasser schütten.** Erster Durchgang eines Labors, das später **Pfade auf Plättchen** prüfen soll (verbundene Wege über die Kanten); hier steht davon absichtlich noch nichts, nur der Ort, an dem es sich prüfen lässt. Drei Handgriffe: „+"/„−" legen einen Ring um die Mitte bzw. nehmen ihn weg (`SOT.hex.ring`, Mitte ist (0,0), also **negative Spalten und Zeilen** — geprüft, dass `r & 1` und die Nachbartabellen das tragen), ein Klick wählt ein Plättchen, die Sortenliste (oder Taste 1–6) gibt ihm seine Sorte. **Übernommen aus `diorama-labor-v1`, absichtlich unverändert**, weil genau das der Befund war, den dieses Labor weiterbenutzen soll: der `Bauplan` (alles in flache Felder, am Ende zu je einer Geometrie verschmolzen, Flächennormalen selbst gerechnet — Facettierung eingebaut, `flatShading` unnötig), die Kachel (Fase, zwei Flankenbänder, Kontaktverschattung **in die Eckenfarben gebacken** statt SSAO), die Palette als **Tokens** (kein `#hex` im JS, darum drehen `?night` und die Tageszeit die Welt mit), orthografische Kamera, VSM-Schatten, Nachbearbeitung aus dem Kern allein (vier `RawShaderMaterial`-Durchgänge, kein `EffectComposer`), und das Zeigen **über das Höhenfeld** statt über einen Netzschnitt. **Weggelassen** — und jedes Mal, weil Beiwerk Fehler verdeckt: Höhenfeld, Wasserrouting, Nebel und Hebung, Klane, Leute, Wetter. **Die eine Umstellung: die Höhe ist eine EIGENSCHAFT DER SORTE**, keine gerechnete Landschaft — Hochebene +2, Felsig +1, Kiesbank −1 Stufen. Damit bleibt die Kontaktverschattung am Leben (sie ist der halbe Grund, warum die Kacheln gemalt aussehen, und macht einen angebauten Ring sofort lesbar), und man weiss trotzdem jederzeit, warum ein Plättchen wie hoch liegt. Nebenbefund, gemessen statt vermutet: ein Strahlgang über alle Plättchenmitten trifft in der Aufsicht **91/91**, bei der Voreinstellung (37°) **91/91**, bei ganz flachem Blick (14°) nur **71/91** — und mit `?stufen=0` wieder 91/91. Die zwanzig fehlenden sind also von der Terrasse davor **wirklich** verdeckt, kein Fehler im Zeigen; darum ebnet **`T`** ein, dieselbe Antwort wie im Diorama. Zwei Speicher, und die Trennung ist der Punkt: die **Sorten überleben das Abbauen eines Rings** (wer ihn wieder anbaut, findet sie vor), die gebauten Plättchen werden bei jedem Aufbau verworfen. Ein Sortenwechsel baut die ganze Arena neu — nicht aus Faulheit: die Kontaktverschattung hängt an den Höhen der **Nachbarn**, wer nur das eine Plättchen umschriebe, liesse sechs Kontakte falsch stehen (bei Ring 4 sind das 61 Plättchen, 9,7k Dreiecke, **49 ms** — der Stempel nennt sie, damit die Behauptung prüfbar bleibt). Der Maßstab ist **abgeleitet** (aus der Silhouette im Kamerasystem, also inklusive Drehung und Neigung) mit einer Untergrenze von 4,4 Feldbreiten: ein einzelnes Plättchen füllte sonst das Bild und läse sich als Wand statt als Spielstein. `?zoom=` und das Rad nageln ihn fest, „Einpassen" gibt ihn zurück. Der Stand ist die URL: jede Sorte wird nach `?sorten=` zurückgeschrieben. **Zweiter Durchgang: das Höhenfeld, und die Minikarte als seine Ansicht.** Damit hört die Arena auf, ein Haufen gleich hoher Steine zu sein. Ein Feld ist eine **reine Funktion von (c,r)** — kein Speicher, keine Reihenfolge, kein Zustand; ein Feld zu wechseln heisst nicht, Höhen umzuschreiben, sondern eine andere Funktion zu fragen. Daraus folgt der eigentliche Gewinn: **die Minikarte malt denselben Wert, den die Kachel bekommt** (`f.schau`), es gibt also keine zweite Wahrheit fürs Bild. Sieben Felder — `flach` (Gegenprobe) · `nord` · `ost` · `kuppe` · `senke` · `kamm` · `rauschen` —, geblättert mit **F**, dazu `?hub=` (Bild ↑↓). **`hub` ist absichtlich EIN Hebel für zwei Dinge:** die Höhe zwischen Schwarz und Weiss *und* die Zahl der Ebenen. Damit fällt kein Rest an — jedes Plateau liegt genau eine Terrasse über dem nächsten, und das ist, was die Kachelbauweise sehen will; `?stufenlos` ist die Gegenprobe und liest sich sofort als Gelände statt als Brett. **Feld und Sorte addieren sich**, jeder Hebel einzeln abschaltbar (`?hub=0` · `?stufen=0`) und darum einzeln beurteilbar; vermischt wäre nicht mehr zu sagen, wovon eine Stufe kommt. Gehoben wird nur nach oben, nie unter die Grundebene: sichtbar ist ohnehin nur der Unterschied, und so bleibt der Boden jeder Kachel auf `UNTEN` — die Platte hängt nicht durch und der Auswahlstrahl behält seinen unteren Anschlag. **Befund: jedes Feld muss seine Spanne ausnutzen, sonst bedeutet `hub` bei jedem Feld etwas anderes.** Verläufe und Kuppe erreichen ihre Enden von selbst, weiches Wertrauschen **nicht** — es lag zwischen etwa 0,25 und 0,8 und hob die Arena bei gleichem Hub nur halb so hoch wie „Kuppe". Man hätte den Unterschied dem Feld angelastet statt der Skala. Jetzt wird je Aufbau einmal über die Arena normiert (Ringzahl, nicht fester Bereich: ein Rauschen auf drei Ringen ist ein anderes Bild als auf acht). Radiale Felder gehen dabei über `SOT.hex.dist` und nicht über den Pixelabstand — sonst wird eine Kuppe zur Ellipse, weil eine Zeile nur 0,866 Feldbreiten hoch ist. Die **Minikarte** ist SVG, nicht ein zweiter three-Durchgang (ein Messgerät muss scharf sein und nichts von Licht, Bewuchs oder Kamera wissen), färbt in **CSS über `color-mix` der Tokens** statt in JS — damit kippt der Graukeil mit der Nacht mit, ohne Neuaufbau, und es steht kein `#hex` im Quelltext. Auswahl und Zeiger ändern nur **Klassen**, nicht 217 Polygone je Mausbewegung; Zeigen und Wählen laufen über EINE Stelle (`ueberSetzen`), also zeigt die Minikarte denselben Ring wie das Diorama und umgekehrt. **Sie ist damit nebenbei die Antwort auf das Verdeckungsproblem:** gemessen trifft ein Strahlgang über alle Plättchenmitten bei `rauschen`/Hub 5 und in der Aufsicht **91/91**, bei `kuppe`/Hub 8 aber nur 89/91 und bei `senke`/Hub 6 stufenlos 88/91 — die Fehlenden sind von der Terrasse davor wirklich verdeckt, und in der Minikarte liegt jedes von ihnen offen. **Dritter Durchgang: die Quelle und ihr Lauf — GERECHNET, nicht gezeichnet.** Ein Plättchen wählen, **Q**, und von dort wird der Weg des Wassers bestimmt: durch die **Feldmitten**, nie bergauf, kürzester Weg, zum tiefsten erreichbaren Punkt. Gezeigt wird er als Linie (Minikarte) und als flaches Band im Diorama — eine **Markierung wie der Auswahlring**, unbeleuchtet und ohne Tiefenschreiben, ausdrücklich kein Wasserband: wie ein Fluss aussieht, ist eine eigene Frage, und sie hier mitzubeantworten hiesse, zwei Dinge auf einmal zu prüfen. **Drei Befunde haben die Regel geformt.** (1) **Strenges Gefälle steht sofort still.** Die Höhen sind auf ganze Stufen gerundet — bei Hub 5 gibt es sechs Höhen für hundert Felder, fast jedes Feld hat also gleich hohe Nachbarn und keinen tieferen; ein reiner Steilabstieg endet nach einem Schritt. Wasser läuft über ein Plateau, bis es einen Abfluss findet — erlaubt sind darum Schritte auf **gleich hohe oder tiefere** Nachbarn, verboten nur bergauf. (2) **Der zweite Schlüssel ist keine Kosmetik:** bei gleicher Schrittzahl gewinnt der Weg mit der kleineren Summe der Höhen *über dem tiefsten Punkt* — von zwei gleich langen Wegen nimmt das Wasser den, der früher fällt, statt oben am Plateaurand entlangzuspazieren. Gemessen wird gegen den tiefsten Punkt und nicht gegen Null, **weil beide Kosten nicht-negativ sein müssen**: eine Kiesbank liegt bei −1 Stufe, mit rohen Höhen könnte die Summe entlang eines Weges *sinken* und die Reihenfolge, in der Dijkstra Felder abschliesst, wäre ungültig. (3) **Das Ziel wird gefunden, nicht vorgegeben.** „Der Weg zum global tiefsten Feld" existiert oft nicht, ohne bergauf zu gehen; gesucht wird darum unter allen *erreichbaren* Feldern das tiefste, bei Gleichstand das nächste. Ist der tiefste Punkt erreichbar, kommt genau er heraus — sonst endet der Lauf in einer **Senke**, und der Bericht sagt das ausdrücklich, statt einen Lauf zu zeigen, der so aussieht, als wäre er angekommen. Geroutet wird auf **`hLauf` = Feld + Sorte OHNE die Unruhe**: die verzieht jede Ecke um ±0,027, und darauf geroutet hätte jedes Plateau ein zufälliges Gefälle — ein Lauf liefe scheinbar sauber bergab und folgte in Wahrheit dem Eckenrauschen (derselbe Schnitt wie im Diorama: fliessen auf `fill`, zeichnen die terrassierte Ansicht). **Geprüft, nicht behauptet:** ein Lauf von JEDEM der 61 Felder aus, über sechs Feldkonfigurationen, gegen eine unabhängige BFS-Referenz — 0× bergauf, 0 Lücken in der Nachbarschaft, Schrittzahl und Zielhöhe stimmen überall mit der Referenz überein. Dabei ein Befund über das SPIEL, nicht über den Code: bei `nord`/Hub 4 mit gewürfelten Sorten enden **35 von 61** Läufen in einer Senke statt am tiefsten Punkt — die verstreuten Kiesbänke (−1 Stufe) stanzen Pfannen in den sonst glatten Verlauf. Sorten sind damit kein Anstrich: sie verändern die Entwässerung. **Vierter Durchgang: Senken füllen, und daraus entstehen SEEN.** Ein See wird nicht gesetzt, er *entsteht* — eine Pfanne füllt sich, bis sie über ihren tiefsten Rand läuft. Priority-Flood liefert das in einem Durchgang: Spiegel, Tiefe je Feld und Überlauf. **Die eine Entscheidung vorweg war, wo das Wasser die Welt verlässt.** Das Diorama flutet vom KARTENRAND einwärts, weil dort das Tal aus der Karte fällt; eine geschlossene Arena hat keinen solchen Rand, und vom Rand einer Schüssel geflutet liefe die ganze Arena bis oben voll (für ein abflussloses Becken sogar richtig, aber nicht gemeint). Geflutet wird darum von den **tiefsten Feldern der Karte** aus. Daraus folgt das Erwartete für jedes Feld von selbst, und es ist nachgemessen: Schüssel und Kuppe ergeben **0 Seen** (beide entwässern vollständig), Seen wachsen nur, wo wirklich eine Pfanne steht. **Ohne das ε des Diorama.** Dort steht `max(h, fill + ε)`, damit jedes Feld einen *echt* tieferen Nachbarn hat; auf unserem stufenweise gerundeten Feld würde dieses ε jedes Plateau in ein Scheingefälle verwandeln, dessen Richtung aus der **Flutreihenfolge** kommt statt aus dem Gelände — der definierte Gleichstands-Entscheid des Laufs wäre still durch eine willkürliche Reihenfolge ersetzt. `fill` liefert hier die Seen, die Regel des Laufs bleibt. **Der eigentliche Gewinn ist der Lauf:** geroutet wird jetzt auf `hFuell`, der Wasseroberfläche, und damit **verschwindet die Sackgasse durch Konstruktion** — nach dem Fluten hat jedes Feld einen nicht-steigenden Weg zum Abfluss. Das Queren eines Sees braucht keinen Sonderfall: seine Felder haben alle denselben Spiegel, es ist also eine Plateauquerung, die die bestehende Kürzeste-Wege-Regel auf direktem Weg zum Überlauf erledigt. Gemessen, mit `?fuellen=0` als Gegenprobe: bei `nord`/Hub 4 mit gewürfelten Sorten **17 → 0** Felder ohne Abstieg und **17 → 0** Läufe, die in einer Senke enden; bei `rauschen`/Hub 6 **48 → 0**. Beide Zahlen sind in der Gegenprobe identisch — sie messen dasselbe von zwei Seiten. **Ein See ist zusammenhängend UND auf einem Spiegel**, nicht bloss „beide nass": zwei Pfannen können sich berühren und auf verschiedenen Höhen stehen, sie zu verschmelzen hiesse eine Wasserfläche behaupten, die in Wirklichkeit eine Stufe hat. Der **Überlauf** ist der tiefste Nachbar ausserhalb, und dass das genau der Pass ist, folgt aus dem Fluten (läge dort ein tieferes Feld, wäre die Flut dort hindurch gelaufen und der Spiegel tiefer) — geprüft über sieben Konfigurationen: die Überlaufhöhe stimmt **ausnahmslos** mit dem Seespiegel überein, und kein Überlauf liegt im eigenen See. Ebenso geprüft: `fill ≥ h` überall, jeder See auf genau einem Spiegel, jedes Seefeld wirklich unter seinem Spiegel. **Die Fläche kommt aus dem IDEALEN Sechseck**, nicht aus den Kachelecken: die sind je Feld geschrumpft und um ±0,027 verzogen, eine Wasserfläche daraus hätte an jeder Feldgrenze eine Naht und läse sich als Fehler. Ideal gebaut stossen die Nachbarn mathematisch genau aneinander, und die ein bis zwei Prozent Überstand sehen von selbst aus wie Wasser am Ufer. Gefärbt wird je Feld nach Tiefe — der Spiegel bleibt eine Ebene, die Farbe erzählt, was darunter liegt. **Und ein Befund über das Spiel, mit drei Gegenproben eingekreist:** auf dem glatten `nord`-Verlauf stammen die sieben Seen **ausschliesslich** aus der Mischung der Sortenhöhen — `sorten=g` ergibt 0 Seen, `sorten=s` (durchgehend Kiesbank, also ein gleichmässiger Versatz) ebenfalls 0, und `?stufen=0` bei gewürfelten Sorten auch 0; erst gemischte Höhen stanzen Pfannen. Sorten sind damit kein Anstrich: **sie erzeugen die Seen.** Das ist der Punkt, an dem zu entscheiden ist, ob eine Sorte überhaupt die Höhe verschieben soll. **Fünfter Durchgang: Quellen SCHÜTTEN Wasser.** Eine Quelle ist keine Marke mehr, sondern eine Menge (`?schuettung=`, 1 = ein Bach). Drei Folgen, und alle drei waren der Grund: **(1) die Menge summiert sich talwärts** — unterhalb eines Zusammenflusses trägt der Lauf, was beide Quellen schütten, und man SIEHT es, weil das Band seine Breite aus der Klasse nimmt (Bach · kleiner Fluss · Fluss · grosser Fluss · Strom, Namen und Vielfachen-Schwellen wie im Diorama). **(2) Eine Pfanne ohne Zufluss bleibt TROCKEN** — das war der offene Punkt des vierten Durchgangs, wo das Gelände allein jede Pfanne zum See machte (auf `nord` mit gewürfelten Sorten sieben Seen ohne Grund). Gemessen: mit EINER Quelle auf dem höchsten Feld bleiben von denselben sieben Pfannen **2** übrig, bei `rauschen` von fünf **0**; erst wenn jedes Feld eine Quelle ist, sind es wieder alle. Seen brauchen jetzt einen Grund. **(3) Der See gibt weiter, was er bekommt** — er unterbricht den Lauf nicht, er ist eine Station darin. **Aufsummiert wird entlang der Läufe, ohne ein zweites Netz.** Dass das die richtige Summe ergibt, hängt an optimaler Teilstruktur: beide Wegkosten sind additiv, also ist der Restweg ab einem Feld nur eine Funktion DIESES Feldes — treffen sich zwei Läufe, laufen sie ab dort gemeinsam weiter, und jedes Feld unterhalb wird von beiden Quellen genau einmal gezählt. **Geprüft im härtesten Fall (jedes Feld eine Quelle), über fünf Konfigurationen:** kein einziger Nachfolger-Konflikt (kein Feld bekommt zwei verschiedene Abflüsse — die Teilstruktur-Behauptung hält), **Knotenbilanz überall exakt** (`q` = eigene Schüttung + Summe der Zuflüsse), die Menge nimmt talwärts nie ab, und die **Menge ist erhalten**: was die Mündungen tragen, ist genau was alle Quellen schütten (91/91 · 273/273 · 127/127). **Die trockene Pfanne sieht nach einem Zirkel aus und ist keiner:** gerechnet wird auf der gefüllten Fläche, erst danach fallen ungespeiste Seen weg — läge eine davon auf einem Lauf, bekäme sie Wasser und wäre nicht ungespeist. Der Festpunkt ist stabil, es braucht keine zweite Runde. Gezeichnet wird das **NETZ** und nicht Lauf für Lauf (sonst lägen unter einem Zusammenfluss zwei Bänder übereinander und sichtbar wäre das zuletzt gezeichnete, nicht das breitere): je Feld ein Stück talwärts in der Breite SEINER Menge, also wächst das Band genau dort, wo die Menge wächst. **Innerhalb eines Sees wird nichts gezeichnet** — ein Fluss quer über eine Wasserfläche liest sich falsch; er verschwindet am Ufer und kommt am Überlauf wieder heraus, wie auf einer Karte. In der Minikarte ist ein gespeister See blau, eine **Pfanne ohne Zufluss** behält ihr Grau und bekommt einen gestrichelten Rand: kein Gewässer, aber der Ort, an dem eines entstünde — und genau das will man beim Entwerfen sehen. **Noch nicht gebaut:** eine Schüttung JE Quelle (heute ein Hebel für alle — die grosse Quelle und der Rinnsal daneben sind noch nicht unterscheidbar), und Verluste (Verdunstung, Versickerung), ohne die ein See im Beharrungszustand immer bis zum Überlauf steigt, sobald überhaupt etwas ankommt. Eine Quelle zu setzen baut die Welt **nicht** neu (die Höhen ändern sich nicht): 2 ms statt 60 ms, und das merkt man bei einem Werkzeug zum Herumprobieren. Debug: `?ringe=` `?sorten=` (Folge in Ringfolge · ein Buchstabe füllt alles · `zufall` würfelt aus der Saat) `?wahl=c,r` `?quellen=c,r;c,r` `?schuettung=` `?fuellen=0|1` `?feld=flach|nord|ost|kuppe|senke|kamm|rauschen` `?hub=` `?stufenlos` `?feldkehr` `?sicht=iso|oben` `?azimut=` `?neigung=` `?zoom=` `?zeit=` `?seed=` `?stufen=` `?unruhe=` `?ao=` `?dichte=` `?post=` `?schatten=` `?lichtdreht=` `?gitter` `?still` `?hilfe`. **Braucht `vendor/three-0.185.1/`** und darum einen Server oder `--allow-file-access-from-files` — bootet der Modulteil nicht, sagt die Seite es nach 2,5 s selbst. Offen: **das Gewässer zum Lauf** (heute ist er eine Linie durch die Feldmitten; gezeichnet gehört er über Ports auf den Kantenmitten), **Schüttung je Quelle** (heute ein Hebel für alle), **Verluste** (ohne sie steigt jeder gespeiste See bis zum Überlauf), **ein Feld von Hand malen** (die Minikarte wäre die Fläche dafür — heute wählt sie nur), **die Pfade selbst** (sie hängen an den Kanten, nicht an den Feldern — die Ports gehören auf die Kantenmitten, und die Tangente dort auf die Verbindung der zwei Feldmitten, sonst knickt jede Naht; darum steht noch kein `kanten`-Feld im Datenmodell, ein leeres Feld „für später" beweist nichts), Drehen eines Plättchens, und die Frage, ob eine Sorte überhaupt vorgibt, welche Pfade sie tragen kann. |
| `bildstil-labor-v1.html` | `drafts/` | active | **Vom Rendering zur Zeichnung — dieselbe Welt, fünf Bilder.** Prüffrage: das Diorama sieht poliert und volumetrisch aus, die Kunstrichtung verlangt aber „stilisierte, fast **holzschnittartige** Illustration … kein Realismus, **kein Pixel-Art**, kein Comic" (`art-direction-handbuch.html`, Karte „Stil"). Was fehlt dazwischen? Das Labor beantwortet es nicht mit Worten, sondern mit einem Schalter über dem unveränderten Weltaufbau von `diorama-labor-v1`: `jetzt` (Vergleichsmarke) · `holzschnitt` · `papier` · `raster` · `pixel`. Die fünf sind **keine fünf Schalter, sondern Voreinstellungen über sechs Hebeln** (`stufen` · `kontur` · `korn` · `kochen` · `raster` · `pixelig`, dazu `kante`, `schattenton`, `strich`, `farbstufen` und die Fotografie `post`) — wer streitet, streitet über einen Hebel, nicht über einen Namen. **Zwei Ebenen:** die Familie sagt, welche Frage gestellt wird, die **Spielart** sagt, wie hart — jede Familie hat vier, erreichbar über den Pfeil am Knopf oder `?variante=` (`holzschnitt`: klassisch · hart · feder · ohne Linie · `papier`: bogen · Bütten · aquarell · skizze · `raster`: risografie · zu wenig · feinraster · siebdruck · `pixel`: grob · fein · ohne Raster · gerastert). Die Spielarten liegen **absichtlich weit auseinander** statt fein abgestuft: zwischen `hart` (zwei Tonstufen, kein Zwischenton) und `feder` (sechs Stufen, fette Linie) liegt der ganze Spielraum der Familie, und wer beide gesehen hat, kann sagen, wo dazwischen er hin will — eine Reihe ähnlicher Vorschläge könnte das nicht. **Befund 1: der ganze Sprung steckt in `stufen` und `schattenton`, nicht in der Linie.** Belegt durch Gegenprobe: `?stil=holzschnitt&kontur=0` liest sich weiter gezeichnet, `?stil=holzschnitt&stufen=0` liest sich wieder gerendert. Die Quantisierung baut three's Beleuchtung nicht nach, sondern **liest sie zurück** — der Quotient aus beleuchteter und Grundfarbe *ist* der Lichtfaktor, und ein Faktor lässt sich stufen. Gebaut wird der Korridor als **Stempel entlang der gezeichneten Mittellinie** (die geglätteten Proben MIT ihren Auslenkungen — darum liegt das Band immer im Korridor): Hex-Scheibe mit Radius 0/1/2 je Klasse als Wasser, Ring darum als Ufer, alles als Vereinigung — Wasser schlägt Ufer, die grössere Klasse die kleinere, benachbarte Abschnitte teilen sich ihr Ufer. Damit ist je Plättchen ENTSCHEIDBAR, ob Wasser wirklich hindurchfliesst: zwei Karten (Wasser/Ufer), gegen die Zeichnung, Inspektor und künftig die Spiellogik dieselbe Frage stellen. Gemessen: 36'421 Wasser- und 11'191 Ufer-Plättchen auf Ebene 2, Mehrkosten im Ops-Bau ~20 ms. **Interaktion:** ein Klick wählt immer das angezeigte Plättchen (kein Überfeld mehr); ein Wasser-Plättchen meldet Name (aus der Klima-Zelle unter dem Stempel — der Hauptstrang entspringt im Hinterrhein-Tal und hiesse mit Lauf-Namen bis zum See Hinterrhein), Klasse, Abfluss und **Wasser an N von 6 Kanten**; ein Ufer-Plättchen meldet, an welchem Fluss es liegt und wofür es taugt (Fischplatz · Steg · Mühle · Hafen, je Klasse). Die Wasserkanten des gewählten Plättchens **leuchten auf der Karte auf** — beim Rinnsal genau die zwei Kantenmitten des Durchflusses, beim Ufer die Bauseite: die Platzierungs-Mechanik ist damit sichtbar, bevor es sie als Regel gibt. Der Korridor wird als Plättchen-Schicht unter dem Band gezeichnet (das Band ist die Kunst, die Plättchen sind das Spiel), Legende um **Flussufer** ergänzt, `?hl=kfluss/gfluss` hebt Korridor und Band gemeinsam hervor. **Befund:** der wörtlich übernommene v3-Renderer deklariert im Laufinneren `var L=Math.hypot(…)` — `var` gilt für die ganze Funktion, ein Parameter namens `L` ist ab da eine Zahl. Der Flussraum blieb still leer (L.cols undefined), während `skala` weiter oben noch den echten Wert sah; der Parameter heisst jetzt EBENE. Zweiter Befund derselben Art wie immer: ein Suchtreffer-Anker landete INNERHALB eines Strings und zerriss ihn — wer programmatisch patcht, prüfe das Ergebnis im Browser, nicht im Diff. **Offen am Flussraum:** das gezeichnete Band schneidet die 0,4-km-Kantenmitten noch nicht (die Regel gilt der Plättchen-Topologie, nicht der Kunst), und der Korridor ist Spielraum, nicht Gewässerbreite (drei Plättchen = 1,2 km — der echte kleine Fluss ist 20–50 m breit; im Spiel ist der Raum die Aue, in der der Fluss wandert). **Offen:** die Rechnung endet weiterhin am Rand der Höhenregion (der Rhein verlässt sie nördlich von Basel, alles darunter bleibt gebacken); Rhone und Ticino liegen ausserhalb der gebackenen Flussdaten und werden darum nur grob entwässert (der Genfersee sucht sich sein Ufer ohne Streamburning selbst); Chur rechnet mit 129 gegen 90 m³/s zu nass; Neurechnung am Regler ~340 ms (bei schnellem Ziehen spürbar); keine Vier-Tafeln-Ansicht (eine Karte, die Jahreszeit schaltet um). **Am Wasser offen:** das Delta wächst nicht — dass der Alpenrhein den Bodensee seit Jahrtausenden von Süden auffüllt und sein Ufer nordwärts schiebt, wäre die eigentliche historische Uferbewegung und bräuchte Geschiebe, nicht nur Abfluss; und das Eis FLIESST nicht (es entsteht rein nach Höhe, statt als Gletscherzunge talwärts zu wandern), weshalb der Rheingletscher die Bodenseewanne erst füllt, wenn die Eisgrenze unter 400 m sinkt, statt aus den Alpen hineinzustossen.
